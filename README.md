# Asphalt 6 arm64 兼容层

让 2011 年发布的《狂野飙车 6》（Asphalt 6: Adrenaline，iOS 1.3.2）在现代 iPhone（arm64，iOS 17 及以上）上运行的兼容层。

本仓库**只包含兼容层代码**，不包含游戏程序、原版美术或音频。使用者需要自备合法取得的游戏 IPA，在自己的 Mac 上构建出可安装的 App。

## 兼容层提供的能力

- **运行环境**：在 arm64 上执行游戏程序，提供它依赖的 iOS 3/4 时代系统接口（UIKit、Foundation、OpenGL ES、音频、触控、重力感应、线程与文件）。
- **全面屏适配**：画面按现代屏幕比例与安全区重新布局，界面元素（返回键、跳过键、选车按钮等）随之调整。
  - 已测试机型：iPhone 17 Pro（iOS 27.0）；
  - 暂不支持 iPhone Duo。
- **图形兼容**：OpenGL ES 调用适配到当前驱动；构建时为三段旧着色器做声明修正，使其能在当前驱动上编译。
- **音乐**：游戏自带音乐由本机音频服务播放，可正常暂停、恢复。
- **稳定性**：
  - 后台加载（例如快速切换车辆）时，游戏线程会把执行权优先让给主线程，画面和触控持续响应，不会被系统看门狗终止；
  - 离线事件队列文件（`Documents/events.dat`）超过 1MB 时会在启动前自动移开，避免它无限增长导致启动失败。
- **可选高清背景包**：见下文。

## 工作原理

### 提前编译，而非运行时转换

游戏的 ARMv7 程序在**构建时**一次性转换成 C++ 源码（3214 个程序模块），再由 Xcode 的 clang 编译成 arm64 机器码，与兼容层一起链接进 App。

手机上运行的全部是这些预先编译好的 arm64 代码：

- 运行时不生成任何代码（没有 JIT），也不逐条解释指令；
- 做法与 Rosetta 2 的提前转换类似，App 不需要任何特殊权限。

### 为什么比原生程序慢

转换后的代码要逐条保持与 ARMv7 原版完全一致的行为，因此它更像一个“静态编译好的模拟器”：执行的是原生指令，但原版的每条指令通常需要几条 arm64 指令来实现。

- **寄存器**：ARMv7 的寄存器保存在内存中的一个结构体里。寄存器优化让它们在一个基本块内留在真实的 CPU 寄存器中，块与块之间再写回；
- **内存**：游戏看到的是原版的 32 位地址空间，每次读写都要经过地址换算与边界检查；
- **条件标志与浮点**：条件标志逐条计算；浮点运算按 ARMv7 的舍入、非规格化数与 NaN 规则逐位还原（软件浮点），在能保证结果一致的常见情况下直接使用硬件运算；
- **函数调用**：通过函数指针跳转、调用系统函数时，需要查表找到对应的转换代码或兼容层实现（结果有缓存）；
- **执行切片**：代码按固定预算分段执行，便于线程调度和音频服务插入。

“当前状态 → 帧率”一节中的几项优化，都是在削减这部分开销。

### 系统接口

游戏调用的 iOS 3/4 时代系统接口（UIKit、Foundation、OpenGL ES、音频、触控、重力感应、线程与文件等）由兼容层用现代 iOS 接口重新实现。已经不存在或不再适用的接口，或者替换成等效实现，或者按“不可用”处理（见“已移除的功能”）。

### 构建可复现

转换过程的每一步都有固定的校验值：

- Ghidra 对游戏程序的分析结果；
- 生成的 3214 个程序模块；
- 宿主模块与数据包；
- 资源文件。

只要使用受支持的 1.3.2 IPA，任何人在自己的 Mac 上得到的上述结果都逐字节相同，任何一步不一致都会让构建停下。最终编译出的 App 二进制会随 Xcode 版本略有不同。

## 已移除的功能

以下功能依赖已停止服务或不再适用的系统能力，兼容层将其移除。菜单中对应的按钮在构建资源时替换为不可见、不可点击的空元素，保留原有的元素名称，因此菜单逻辑照常运行，只是入口不再出现。

- **商店与推广**：游戏内购（金币、星星、解锁）、App Store 跳转、“更多游戏”、评分提示及 Gameloft Live 入口全部移除。StoreKit 不会被加载，游戏中不会出现任何购买提示。
- **音乐播放器（iPod）**：原版可以在暂停菜单和声音设置中选择系统音乐库里的歌曲作为比赛音乐，此功能已移除：
  - 暂停菜单中的音乐按钮、声音设置中的播放列表按钮不再显示，歌曲列表页面也无法进入；
  - 游戏查询系统音乐库时一律得到“不可用”，因此始终播放游戏自带音乐；
  - App 不会访问系统音乐库，启动时也不会申请音乐库权限。

## 环境要求

需要自行安装：

| 项目 | 要求 |
| --- | --- |
| Mac | Apple Silicon（M 系列芯片） |
| Xcode | 完整的 Xcode，含 iOS 17 及以上 SDK（仅命令行工具不够） |
| CMake | 3.20 及以上，例如 `brew install cmake` |
| Python | 3.9 及以上（macOS 自带的即可） |

首次运行时自动安装到 `build/`（需要联网，约 800MB）：

| 项目 | 版本 | 用途 |
| --- | --- | --- |
| Python 包 | `scripts/requirements.txt`：capstone 5.0.7、tqdm 4.67.1 | 程序转换、进度显示 |
| Ghidra | 12.1.4（官方发布包，校验 SHA-256；官方包缺少 Apple Silicon 版本机组件，首次使用时自动从其自带源码编译） | 分析游戏程序 |
| JDK | Temurin 21.0.12.1（官方发布包，校验 SHA-256） | 运行 Ghidra |

此外需要自备游戏 IPA：**仅支持 Asphalt 6 1.3.2**（构建脚本会校验其中的程序；1.3.8 等其他版本不受支持。p.s. 因为我一开始就下的1.3.2，不想折腾了），校验值见下。

### 支持的游戏版本

| 项目 | 值 |
| --- | --- |
| 版本 | 1.3.2（`CFBundleVersion`） |
| 已验证的 IPA 文件 | `Asphalt_6__Adrenaline_1.3.2_ios_3.1.3.ipa`，564,685,789 字节，可以自行搜索 Archive.org 获取ipa包 |
| IPA 的 SHA-256 | `30ea95d5ccd3fb9ded3b7b6b0c9e88f6af8de62d8c841ed0a3f79be6d045a796` |
| 游戏程序 ARMv7 部分的 SHA-256 | `4a2209881ab5933113a15770b0615807cfa7d73bf50a9326569a7ed20f77df00` |

构建脚本以**游戏程序 ARMv7 部分**的哈希为准：重新打包过的 IPA，文件哈希可能和上表不同，但只要其中的游戏程序一致，就可以使用。自行核对：

```sh
shasum -a 256 Asphalt6.ipa                                   # IPA 文件
unzip -p Asphalt6.ipa Payload/Asphalt6.app/Asphalt6 > Asphalt6.fat
lipo -thin armv7 Asphalt6.fat -output Asphalt6.armv7
shasum -a 256 Asphalt6.armv7                                 # 游戏程序 ARMv7 部分
```

## 构建

```sh
python3 scripts/buildGame.py /path/to/Asphalt6.ipa
```

脚本分 6 步执行，每一步都用固定的 SHA-256 校验结果，任何不一致都会立即停止：

| 步骤 | 终端显示 | 内容 |
| --- | --- | --- |
| 1 | `[1/6] Preparing toolchain` | 检查 Xcode 与 CMake，安装 Python 包，首次运行时下载 Ghidra 与 JDK |
| 2 | `[2/6] Extracting the game IPA` | 解开 IPA，确认是受支持的 1.3.2 版本 |
| 3 | `[3/6] Building game resources` | 从 IPA 组装出游戏资源文件夹 `Asphalt6Data` |
| 4 | `[4/6] Translating the game program` | 用 Ghidra 分析游戏程序，转换成本机 C++ 源码，再做按基本块的寄存器优化，结果放在 `generated/`（约 20 分钟） |
| 5 | `[5/6] Compiling AOT` | 用 CMake 编译 iOS 静态库（约 1.5–2.5 小时） |
| 6 | `[6/6] Packaging` | 链接并输出未签名的安装包，打包资源 |

下载、分析导出、转换、寄存器优化和编译都会显示进度条；Ghidra 的输出保存在 `build/work/pcode/`，编译的完整输出保存在 `build/compile.log`。

产物位于 `dist/`：

- `Asphalt6ARM64.ipa`：未签名的 App，用 SideStore、AltStore 等工具签名安装；
- `Asphalt6Data.zip`：游戏资源包；
- `NativeArtwork.zip`：仅当本地 `artwork/` 目录放有高清图片时生成（供维护者打包发布用）；一般用户直接下载单独发布的高清背景包即可。

可选参数：

| 参数 | 作用 |
| --- | --- |
| `--jobs N` | 编译并行数，默认为 CPU 核数的一半 |
| `--debug` | 编译时带调试信息（`-g`），便于对照崩溃日志和性能分析；生成的机器码相同，但 `build/ios` 会增大到约 18 GB |
| `--no-promote` | 不做寄存器优化，直接编译转换结果（代码更小、编译更快） |

## 安装

1. 安装 `Asphalt6ARM64.ipa`，并打开一次（会生成 App 的文稿目录和《资源导入说明》）。
2. 在“文件”App 中，把 `Asphalt6Data.zip` 直接放进 **我的 iPhone → （App 名称，取自你的 IPA，通常为 Asphalt 6）**，无需解压。
3. 可选：把高清背景包 `NativeArtwork.zip` 也放在同一目录。
4. 打开 App，兼容层会自动完成解压和验证。

### 启动时的资源处理

| 情况 | 屏幕提示 | 处理 |
| --- | --- | --- |
| 每次启动 | 正在验证游戏资源 | 校验 `Asphalt6Data`（之后启动使用缓存，很快），并检查高清背景是否齐全 |
| 资源缺失或损坏，且有 `Asphalt6Data.zip` | 正在解压资源包 | 删除旧的 `Asphalt6Data`，解压资源包，成功后删除资源包，再重新验证；已安装的高清背景会保留 |
| 资源缺失，且没有资源包 | 请先导入游戏资源 | 导入资源包后点击“重新检测” |
| 资源包损坏 | 资源包 Asphalt6Data.zip 损坏，请先导入新资源包 | 换一个资源包后点击“重新检测” |
| 资源完整，高清背景不全，且有 `NativeArtwork.zip` | 正在解压高清背景包 | 补齐缺失的高清背景，成功后删除压缩包，再重新验证 |
| 高清背景包损坏 | 高清背景包 NativeArtwork.zip 解压失败 | 照常启动游戏；压缩包保留，下次启动再次尝试 |
| 资源完整 | 正在启动游戏 | 此时文稿目录中的压缩包会被忽略 |

## 高清背景包（可选）

高清背景包 `NativeArtwork.zip` 与代码分开、单独发布，不包含在本仓库中。下载后放进 App 的文稿目录即可。启动时如果高清背景不齐全，兼容层会自动：

1. 解压缺失的文件到 `Asphalt6Data/NativeArtwork/`；
2. 逐个校验 SHA-256，只使用校验通过的图片；
3. 标题、菜单、加载等背景改为 16:9 高清版本。

高清背景已齐全时，文稿目录中的 `NativeArtwork.zip` 会被忽略。

没有这个压缩包、或其中某张图缺失或损坏时，对应画面自动使用游戏原版背景，不影响运行。

> 高清背景包中的图片以游戏原版背景为基础，使用 GPT Image 2 重绘成 16:9 画幅，其画面内容与美术设计归 Gameloft 所有。兼容层内置了每张图片的校验值，只会使用与发布版本完全一致的图片。

## 目录结构

| 路径 | 内容 |
| --- | --- |
| `host/app/` | App 入口、启动流程与资源检查界面 |
| `host/src/` | 兼容层主体：系统接口、图形、音频、输入、界面适配、资源与高清背景包 |
| `host/tests/` | 兼容层的独立测试 |
| `aot/runtime/` | 翻译后程序所依赖的运行时：寄存器布局、内存访问、调度接口 |
| `aot/math/` | 与 ARMv7 浮点逐位一致的软件浮点库（源自 QEMU SoftFloat） |
| `artwork/` | 高清背景图片（不提交），存在时构建会打包为 `NativeArtwork.zip` |
| `scripts/buildGame.py` | 一键构建入口 |
| `scripts/as6build/` | 构建各阶段的实现与校验数据 |
| `generated/` | 构建时生成，不提交 |

### 帧率

在 iPhone 17 Pro（iOS 27.0）上实测，场景为生涯第 1 场 · 拿索（第一张地图）。每个版本各跑一局完整比赛，统计比赛过程中（约 2–3 分钟）的画面刷新：

| 版本 | 平均帧率 | 平均每帧耗时 | 超过 16 ms 的帧 |
| --- | --- | --- | --- |
| 基础版本 | 约 36 fps | 25.3 ms | 100% |
| + 寄存器优化 | 约 53 fps | 18.7 ms | 73% |
| + 外部函数调用与间接跳转缓存 | 约 57 fps | 17.4 ms | 56% |
| + NEON 单精度运算硬件快速路径（当前） | 约 59–60 fps | 16.6 ms | 46% |

- 当前版本平均每帧 16.6 ms，与 60 Hz 的帧间隔（16.67 ms）一致，比赛中基本稳定在 60 fps；“超过 16 ms”的统计阈值略低于 16.67 ms，剩余比例主要是垂直同步的正常抖动；
- 比赛中个别场景仍会短暂降到约 55 fps；
- 比赛过程中没有出现超过 100 ms 的卡顿（加载画面除外）；
- 菜单与结算画面稳定在 60 fps。
